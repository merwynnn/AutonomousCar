# Tracks and race rules

## 1. Test track

The PDF test track is a peanut/ring shape with two lobes, a central pinch and a
start/finish line at the bottom. The simulator reproduces it parametrically:

- overall area within 15 × 8 m;
- lane width 0.9 m (configurable 0.8–1.0 m);
- 16 cm high grey pipe walls (160 mm VMC pipe, radius ≈8 cm);
- dark floor;
- start/finish line and direction of travel;
- wall geometry generated from the centreline offset by ±width/2.

The exact PDF dimensions are not annotated; the layout is reconstructed to scale
inside the competition area. The generated track is validated visually against the
PDF rendering.

## 2. Procedural generator

Because the competition track is unknown, the generator produces many valid
variants:

- closed Catmull–Rom / spline centreline;
- random control points inside the 15 × 8 m area;
- width sampled in 0.8–1.0 m;
- curvature constraints (minimum radius) and clearance checks;
- no self-intersection;
- start straight and start/finish line;
- optional obstacles: boxes, cones, pipe barriers, chicanes;
- minimum gap between obstacles and walls so a car can pass.

Every generated track has a seed and is reproducible. Validation rejects tracks
that are too tight, self-intersecting or impossible to drive.

### Obstacles

Obstacle types are configurable:

- box (crate-like);
- cone;
- vertical pipe/barrier;
- optional chicane blocks.

They are static, visible to lidar/ultrasonic, and collision-enabled. Placement
respects a minimum clearance based on car width plus a safety margin.

**Test-track procedural landmarks:** the test track now places eight deterministic
wall-side crates/poles (seeded, alternating sides) at fractions 0.10–0.94 of the
lap. They sit just inside the pipe wall, outside the safe racing line, with
heights 0.22–0.30 m. They are collidable, lidar-visible and rendered in the
dashboard. Their purpose is to add distinctive scan features for SLAM/MCL; they
also make odometry-only control fail earlier, as intended. The exact positions
and sizes are generated by `build_obstacles()` in
`src/awake_sim/tracks/geometry.py` and sent to the dashboard in the track hello
message.

## 3. Track editor

The dashboard includes a lightweight top-down editor:

- drag centreline control points;
- change track width;
- add/move/delete obstacles;
- set start line and direction;
- preview lidar visibility and minimum clearance;
- save/load JSON.

The generator remains the primary workflow; the editor is for deliberate tests
and for reproducing a real layout when one becomes known.

## 4. Track JSON schema

```json
{
  "name": "test_track",
  "version": 1,
  "seed": 42,
  "bounds": [0.0, 0.0, 15.0, 8.0],
  "width": 0.9,
  "centerline": [[x, y], ...],
  "walls": {"height": 0.16, "radius": 0.08, "material": "grey_pvc"},
  "start_line": {"position": [x, y], "heading": 0.0, "width": 0.9},
  "obstacles": [
    {"type": "box", "pose": [x, y, yaw], "size": [0.3, 0.3, 0.2]}
  ]
}
```

The Python schema is validated with pydantic; the web editor uses the same JSON.

## 5. Race rules

- Five consecutive laps; final time is the sum of the five laps.
- A lap counts only if the full loop is completed in the correct direction and the
  start/finish line is crossed.
- Light wall grazing is tolerated.
- A wall impact above the deformation impulse threshold triggers a penalty event
  (2 points on the distance score in the real competition).
- An intervention/repositioning triggers a penalty event.
- The simulator reports both raw lap time and penalized score.

Lap timing is performed by the race manager using ground-truth referee state
(like the official timing), but the controller never sees that state.

## 6. Track validation tests

- Closed loop and correct winding.
- Width within 0.8–1.0 m.
- No self-intersection.
- Minimum curvature compatible with the car’s turning radius.
- All geometry inside the 15 × 8 m bounds.
- Start line on the centreline, perpendicular to travel.
- Obstacles do not overlap walls or each other and leave a drivable gap.
- Lidar can see the walls at the configured mount height.

## 7. Competition-day workflow

1. Generate or load a track close to the practice layout.
2. Run a mapping lap with SLAM at safe speed.
3. Extract the centreline and optimize the racing line and speed profile.
4. Run 5-lap race simulations with `realistic` sensors.
5. Stress-test with `harsh` sensors, latency and obstacle variants.
6. Export the map, controller parameters and strategy notes for the real car.
